# 12 · 同类项目与生态位

> 调研时间：2026-10。以下判断基于公开文档/仓库；具体能力以你实际试用为准。
> 这不是学术综述，是「我要不要重复造轮子」的决策表。

## 12.1 现有项目分四类

### A. Agent Skill / 一句话出片

| 项目 | 做什么 | 强 | 弱 |
|---|---|---|---|
| [Win-Hao/music-mv](https://github.com/Win-Hao/music-mv) | Agent skill：音频 → 分镜 → 像素/拼贴风 MV | 端到端、有工作流、7–10 小时出片 | 风格偏单一；无运镜语法；无时序 QA；无风格锁 |

**结论**：这是最接近的项目。它证明了「Agent 可以做 MV」，但没有解决
「如何稳定地产出电影感、风格统一、可验收」的问题。

### B. 代码化视频框架

| 项目 | 做什么 | 强 | 弱 |
|---|---|---|---|
| [Remotion](https://github.com/remotion-dev/remotion) | React 组件 → 视频 | 生态成熟、音频同步、渲染稳定 | 付费许可（>3 人）；偏 2D/编排 |
| [Motion Canvas](https://github.com/motion-canvas/motion-canvas) | TS 生成器 → 2D 动画 | 时间轴/缓动优雅 | 2D 为主；3D 需自己接 |
| [Revideo](https://github.com/redotvideo/revideo) | Motion Canvas 的视频扩展 | 代码化剪辑 | 生态较新 |
| [Editly](https://github.com/mifi/editly) | JSON → 剪辑 | 简单、适合拼接 | 不是 3D/视觉系统 |
| HyperFrames | Agent 友好的渲染器（公开资料较少） | 面向 Agent | 需自行验证成熟度 |

**结论**：它们解决「怎么把画面编成视频」，不解决「拍什么、怎么拍、怎么验」。

### C. 实时音频视觉

| 项目 | 做什么 | 强 | 弱 |
|---|---|---|---|
| [Butterchurn](https://github.com/jberg/butterchurn) | Milkdrop 预设 → WebGL | 律动强、预设多、MIT | 无叙事/镜头；风格是「可视化」 |
| [projectM](https://github.com/projectM-visualizer/projectm) | Milkdrop 兼容 | C++/桌面 | 同上；LGPL |
| [Hydra](https://github.com/hydra-synth/hydra) | 实时编程视频合成 | 反馈/故障/现场感 | AGPL；无结构；不可控长片 |
| [cables.gl](https://cables.gl) | 节点式 WebGL | 可视化搭建 | 无导演层；导出/确定性一般 |

**结论**：适合做「段落内的视觉」，不适合做「5 分钟有起承转合的片子」。

### D. 生成式视频 / AI MV 工具

| 类型 | 代表 | 强 | 弱 |
|---|---|---|---|
| 文生视频 | Runway / Pika / Kling / Veo | 单镜惊艳 | 一致性差、不可精确重渲、成本高 |
| 音频反应生成 | Kaiber / Neural Frames / Specterr | 快速出片 | 风格模板化、镜头语法弱 |
| 帧插值/风格化 | Deforum / ComfyUI | 风格强 | 时序闪烁、不可控 |

**结论**：这些是「素材生成器」，不是「导演」。可以喂给 mvcraft 做参考帧/纹理，
但不要让它们决定结构。

## 12.3 真正的缺口：导演层

把 MV 制作拆成 8 层：

```
1. 音乐理解      ← librosa/allin1 已解决
2. 创意/母题     ← 人/LLM，但没有方法
3. 分镜/镜头语法 ← 人，但没有可执行规范   ◀ 缺口
4. 美术方向      ← 人，但没有锁             ◀ 缺口
5. 场景实现      ← three.js 已解决
6. 渲染/编码     ← ffmpeg 已解决
7. 时序 QA       ← 工具存在，但没人串起来   ◀ 缺口
8. 交付/合规     ← 人，但没有台账           ◀ 缺口
```

mvcraft 不重做 1/5/6，而是补 3/4/7/8，并把 2 变成可问询的流程。

**为什么这件事值得做**：

- 模型写 Three.js 的能力已经够用；瓶颈在「决策」和「验收」。
- 现有工具都能生成「一段好看的画面」，但没人保证「整片不漂移、不塌、不挡脸」。
- Agent 需要的是**可执行的判断标准**，不是更多 API。

## 12.4 从每个项目借什么

| 来源 | 借什么 | 不借什么 |
|---|---|---|
| music-mv | 端到端 skill 结构、问询、分阶段交付 | 单一像素风、无 QA |
| Remotion | 组件化时间轴、音频同步 API 设计 | 付费许可、React 绑定 |
| Motion Canvas | 生成器/缓动的表达力 | 2D 局限 |
| Butterchurn | 音频驱动的即时满足感、预设思路 | 无叙事 |
| Hydra | 反馈/故障的视觉语言 | AGPL、不可控 |
| allin1 | 段落/节拍 SOTA | 重依赖、Windows 兼容 |
| VMAF | 编码验收 | 把它当审美标准 |
| Poly Haven | CC0 资产的获取方式 | — |
| 电影摄影 | 镜头语法/光比/景别 | 直接复制具体作品 |

## 12.5 为什么不用「一个巨大的提示词」生成全片

诱人方案：把歌和一句话丢给视频模型，生成 5 分钟。

为什么现在不行：

1. **一致性**：角色/场景/光线在长序列里漂移。
2. **可控性**：改一个镜头要重生成全部；无法局部返工。
3. **精确性**：切点对不上拍；字幕对不上人声。
4. **确定性**：同一提示词两次结果不同；无法 QA。
5. **成本**：5 分钟高质量生成的成本远高于程序化渲染。
6. **版权**：训练数据/输出权利不清晰。

程序化渲染的劣势是「需要搭」，优势是**每一帧都可解释、可修改、可复现**。
mvcraft 选后者。

## 12.6 已知限制（诚实版）

- **审美仍依赖人/模型判断**：风格帧选得好不好，决定上限。
- **复杂人物/表演**：程序化做不了细腻表演；需要实拍/AI 素材。
- **歌词敏感内容**：自动对齐/断句仍要人工。
- **大体量场景**：超过 15 万三角形/场景需要更复杂的 LOD/流式加载。
- **QA 不能替代观看**：VMAF 高不代表好看；黑帧检测不代表叙事成立。
- **跨平台**：不同 GPU/浏览器可能有着色器差异；交付前要在目标环境抽帧。

## 12.7 路线图（如果要继续做）

| 优先级 | 事项 | 价值 |
|---|---|---|
| P0 | 通用化 `analyze_audio.py` + `validate-storyboard.mjs` | 让流程可复用 |
| P0 | 模板工程一键换歌/换风格 | 降低门槛 |
| P1 | 时序 QA 脚本（黑帧/冻结/闪烁/VMAF/响度） | 把事故挡在交付前 |
| P1 | 3 个 30 秒示例（墨/城市/极简） | 证明风格库可执行 |
| P2 | 本地 VLM 质检（主体/字幕/构图） | 减少人工抽帧 |
| P2 | 光流运动分析（速度/方向连续性） | 量化「晕不晕」 |
| P3 | 竖版模板 + 自动重构图 | 平台需求 |
| P3 | 歌词强制对齐（WhisperX + 人工校正） | 歌词视频 |
| P4 | Agent 评测集（10 首歌 × 5 风格） | 证明稳定性 |

## 12.8 生态位一句话

> **Remotion 让你用代码剪视频，Butterchurn 让画面跟着音乐跳，
> mvcraft 让你像一个导演一样决定「为什么这样拍」，并且保证它真的成立。**

如果你只想做一个 15 秒的循环视觉，用 Butterchurn/Hydra 更快。
如果你要一部有开头、有峰值、有落点、风格统一、能交付的 MV，用 mvcraft。
